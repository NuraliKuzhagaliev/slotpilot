# Архитектура основного проекта

Next.js 16 App Router + React + TypeScript + Tailwind. Для Sites используется совместимая сборка Vinext; `dev:next` / `build:next` — обычный Next.js. Зависимости зафиксированы pnpm-lock.yaml; пакетный менеджер pnpm 11.25.0.

## Модули
- `src/contracts/domain.ts`, `schema.ts`, `tools.ts` — прежние канонические runtime/JSON Schema контракты и выведенные типы, с добавлением опциональной доступности расходников в Dataset.
- `src/contracts/app.ts` — канонические runtime/JSON-схемы сохранённых сущностей, состояния БД и серверных снимков. Все типы выводятся из схем. `tool-outputs.ts` проверяет ответы всех десяти инструментов. На границе БД проверяется прочитанное и записываемое состояние; неподходящие данные не сохраняются. Входы HTTP валидируются Zod и общими runtime-схемами.
- `src/server/domain/` — прежнее чистое ядро; одинаковое для preview, voice и формы.
- `src/server/app/` — сессии, операции, подтверждения, demo, HTTP-Supabase адаптер.
- `app/api/` — тонкие HTTP маршруты с серверными проверками. Владелец берётся из HMAC-cookie, роль не выбирается моделью.
- `src/features/booking-ui/` — клиент, admin/demo, серверное состояние и подсветка изменённых условий.
- `src/features/voice/` — основной голосовой адаптер. `spikes/voice-access/` остаётся историческим диагностическим стендом.
- `public/audio/` — AudioWorklet/PCM без секретов.
- `supabase/migrations/001_slotpilot.sql` — PostgreSQL, транзакционный CAS, exclusion constraints, RLS без браузерных политик и серверные RPC с SECURITY INVOKER.

## Хранение и атомарность

Для маленького семидневного демо используется одна JSONB-запись состояния на namespace (обращения, действия, согласия, записи, журнал). Это намеренное упрощение, не масштабируемая CRM. Резервирования вынесены в отдельную реляционную таблицу с `tstzrange [)` exclusion constraint по namespace/виду/ID ресурса.

Сервер читает состояние и ревизию; чистые операции пересчитывают все правила. `slotpilot_commit` блокирует строку namespace, сравнивает ревизию и в **одной транзакции** сохраняет новое состояние вместе с обоими ресурсами. Если конкурент изменил данные, операция повторяется от свежего состояния. При пересечении ресурсов PostgreSQL откатывает всю функцию. Поэтому неудачный перенос оставляет исходную запись.

Подготовка не удерживает время. Выполнение требует actionId, владельца, ожидаемой версии, срока и отдельной evidence. Результат actionId сохраняется вместе с записью. Повтор возвращает прежний результат даже после истечения срока. Аудиоперебивание не откатывает сохранённое действие.

## Согласие

Кнопка выдаёт evidence через авторизованный same-origin endpoint. Голос передаёт только законченные transcript.user; allow-list принимает короткие однозначные подтверждения и отвергает «yes, but…». Evidence привязана к actionId и текущему подготовленному снимку. Новый старт речи инвалидирует ещё неисполненные голосовые evidence. Частичные расшифровки не дают согласия.

Ограничение: браузер транспортирует транскрипт; это не криптографически подтверждённая расшифровка провайдера. Пользователь не может изменить чужую запись, но может имитировать подтверждение собственных тестовых действий через свою авторизованную сессию. Не выдавать это за юридически значимое голосовое согласие.

## Быстрые перебивания

Режим `min_latency`, `interruption_delay: 0`; без переопределения адаптивных min/max silence. По input.speech.started очередь очищается. После interrupted блокируются поздние фрагменты прежнего reply_id. Дополнительно устойчивый входной сигнал на пяти 20-ms кадрах вызывает локальное отключение аудио до сетевого ответа. Это эвристика, а не измеренный SLA: громкий шум может дать ложное прерывание. Эхоподавление и шумоподавление включены. Новый живой прогон обязателен.

## Границы

Preview без настроенной базы ничего не сохраняет и не выдаёт записи. Реальное сохранение требует Supabase. Нет SQLite/localStorage-подмены. Запросы к AssemblyAI идут напрямую из браузера по временным токенам. Постоянный ключ, серверный ключ БД и session secret остаются только на backend.

Подсказки модели обновляются после ручных изменений. Очередь возвращает tool.result только после reply.done; запоздалый результат не озвучивается. Результаты записывающих действий сверяются независимо от состояния звука.

Сервер использует SUPABASE_SECRET_KEY через заголовок apikey; старый SUPABASE_SERVICE_ROLE_KEY сохранён для совместимости и отправляется как JWT. Secret API key не передаётся в Authorization как JWT. Секреты хостинга управляются отдельно от исходников.
